- **Cambia per chi già usa AIW (sicurezza)**: l'elenco qui sotto dice cosa è diverso in un'installazione esistente.
  - La rete dei comandi di shell ora ha un'impostazione, `sandbox.shell_network` (`off` | `on`, solo a livello di macchina; un workspace può solo restringerla). Le **nuove** installazioni partono con `off`. Le installazioni **esistenti** restano a `on`: al primo avvio una migrazione scrive `on` in modo esplicito nella configurazione globale (una volta sola, segnata dal file `.shell-network-migrated`) e in Sicurezza → Sandbox compare un avviso, chiudibile. Se un comando fallisce perché la rete è spenta, il risultato aggiunge: «La rete della shell è spenta: per installare pacchetti o scaricare file attivala in Sicurezza → Sandbox». Su Linux chiude la rete `--unshare-net`, su macOS `(deny network*)`; **su Windows non si può chiudere** e l'interruttore non ha effetto sui comandi.
  - L'argomento `network` del tool shell può solo chiudere la rete ancora di più, mai aprirla.
  - Con la sandbox attiva (Linux e macOS; su Windows solo per i tool di file) la cartella dei dati di AIW e le cartelle di `sandbox.deny_read` (`.ssh`, `.gnupg`, `.aws`, gcloud, `.kube`, docker, `.netrc`, `.npmrc`, `.pypirc`, profili dei browser, portachiavi; modificabile in Sicurezza → Sandbox) sono nascoste ai comandi. Skill e allegati di sessione restano leggibili. **I tool di file (read, grep, glob, …) rifiutano le stesse cartelle** quando la sandbox non è `off`. Compromesso: `git` via SSH non trova più la chiave in `~/.ssh`; togli la cartella dall'elenco per consentirlo.
  - Ai comandi non arrivano più le variabili d'ambiente che sembrano segreti (`*_TOKEN`, `*_KEY`, `*_SECRET`, `*PASSWORD*`, `AIW_*`, credenziali cloud), **anche con sandbox `off`**; si riammettono per nome in `sandbox.env_allow`. Su Linux la sandbox isola anche lo spazio dei processi (`--unshare-pid`).
  - Policy: per il tool shell la riga viene divisa in comandi semplici. «Consenti» con un pattern vale solo se **ogni** comando è consentito e l'analisi è sicura; «Nega» e «Chiedi» valgono se il testo o **uno qualsiasi** dei comandi corrisponde. Quindi `git status && curl …` con la sola regola `git *` ora **chiede conferma** (prima era consentito) e `git status; rm -rf x` con una regola «Nega» `rm *` ora è **negato**. Il soggetto della policy per la shell è solo il comando (un argomento in più non sposta più la corrispondenza). Versione PowerShell inclusa. L'editor delle regole mostra come viene letto un comando composto; nuova rotta `POST /api/policy/analyze`.
- Server MCP stdio con isolamento: nuovo campo `sandbox` (`off` | `read-only` | `workspace-write`) e `sandbox_network`. I **nuovi** server dall'interfaccia partono `workspace-write` con la rete accesa; quelli **esistenti** restano `off`, con l'etichetta «non isolato» e il pulsante «Isola». Un server isolato riceve solo un ambiente di base più le variabili configurate, con `HOME` in una cartella privata, e non vede la cartella dei dati né le cartelle di `sandbox.deny_read`. Un server `off` continua a ereditare tutto l'ambiente. **Su Windows l'isolamento non è disponibile** (un server con isolamento richiesto non parte).
- Conferma dei comandi MCP: la prima volta che parte un comando nuovo o cambiato l'interfaccia chiede «Questo server esegue il comando … su questo computer»; si salva l'hash di (comando, argomenti, nomi delle variabili). Solo con il token `owner` (`POST /api/mcp/servers/{id}/approve`; tutta `/api/mcp/servers/**` richiede l'ambito `full`); una definizione che viene da un workspace o da un'importazione non è mai approvata da sola. **Per chi già usa AIW**: i server stdio già configurati vengono approvati una volta sola alla migrazione (altrimenti si fermerebbero tutti); da lì in poi ogni cambio di comando, argomenti o nomi delle variabili chiede di nuovo.

- Token di accesso per dispositivo e per app (`crates/aiw-engine/src/tokens.rs`, tabella `api_tokens`): `aiw_` + 256 bit casuali, nel database solo un hash con sale (il valore si vede una sola volta), tipi `owner`, `device`, `gateway`, scadenza facoltativa, ultimo uso e indirizzo, revoca che ferma subito anche gli SSE aperti, rotazione. Il pairing ora dà a ogni dispositivo un token suo (legato al suo id e al suo nome, che `POST /api/pair` accetta); scollegarlo, o che il dispositivo stesso lo lasci con `DELETE /api/auth/token`, lo revoca. Anche tra due computer ogni direzione è un pairing distinto e revocabile.
- Ambiti applicati in un solo punto (`crates/aiw-server/src/scopes.rs`): `full` (questo computer), `device` (chat, sessioni, approvazioni, voce, elenchi; non impostazioni di macchina, segreti, modifica di MCP/hook/policy/agenti, canali, token, importazioni da percorso), `gateway` (solo `/v1/*`), `a2a`, `mcp`. Una rotta senza voce richiede `full`; un test legge le rotte registrate e fallisce se una manca.
- API `GET/POST /api/tokens`, `DELETE /api/tokens/{id}`, `POST /api/tokens/{id}/rotate` (solo `full`), registro delle attività per creazioni, revoche, rotazioni e usi di token revocati o scaduti (limitati nel tempo), limite ai token errati per indirizzo (10 ogni 10 minuti, poi 429). CLI `aiw tokens list|create|revoke|rotate`. Interfaccia: Sicurezza → Accessi (dispositivi con «Scollega»; in modalità Sviluppatore «Nuovo token per un'app» con esempio `OPENAI_BASE_URL`) e lo stesso elenco in Dispositivi.
- **Cambia per chi già usa AIW**: il token unico esistente diventa il token `owner` (CLI e shell desktop continuano a funzionare senza far nulla); da un'altra macchina **senza TLS** il token `owner` vale come un dispositivo accoppiato (non apre più impostazioni di macchina, hook, MCP, canali, token), con l'intestazione `x-aiw-notice`; i dispositivi accoppiati prima di questa versione hanno in mano proprio quel token e non si possono migrare uno per uno: vanno accoppiati di nuovo per avere un token loro. Un token da dispositivo non è «locale» nemmeno da loopback. Un token revocato o scaduto dà 401 anche da loopback.
- TLS per la LAN (`server.tls` = `off` | `self_signed` | `files`, con `server.tls.cert_file` e `server.tls.key_file`; solo a livello di macchina): rustls con un acceptor scritto a mano e `rcgen` (niente OpenSSL). `self_signed` crea un'autorità locale e un certificato per nome host, `localhost` e indirizzi di rete (rinnovato se cambiano o a meno di 30 giorni dalla scadenza), chiavi in `<dati>/tls/` con permessi 0600. Il pairing porta l'impronta SHA-256 (QR con `&fp=`, risposta di `/api/pair`); i client Rust verso un dispositivo accoppiato (pairing, runtime `aiw-peer`, MCP, A2A) verificano solo quell'impronta con un verificatore rustls proprio, mai le radici di sistema. Con TLS acceso il listener non risponde all'HTTP in chiaro dalla rete (da loopback sì, per i client di questo computer), `Origin` `https://` e HSTS gestiti; con LAN e TLS spento compare un avviso in `aiw serve` e in Sicurezza → Rete. `GET /api/tls`, `GET /api/tls/ca.pem` per installare l'autorità in un browser.
- Limiti noti: un browser su un altro dispositivo non può fissare il certificato (avviso finché non si installa l'autorità); mai provato su due computer o telefoni reali (test con listener TLS locale e handshake in memoria); niente di mobile compilato; server MCP e agenti A2A inseriti a mano usano le radici di sistema; il token `owner` sta in chiaro nel file `token` (0600) e si cambia cancellando il file.

- Router automatico dei runtime (`crates/aiw-engine/src/router.rs`): un profilo con `runtime_id: "auto"` (e i profili `auto:*` dell'adviser) sceglie il runtime quando parte il run, con una funzione di ordinamento pura (`rank`) e una tabella di preferenze documentata nel modulo: dove gira il modello (tutto su GPU nativa, su GPU portabile o NPU, diviso tra GPU e RAM, CPU), pronto prima di «da avviare», poi `route_priority` del manifest. Ogni candidato ha il motivo del suo posto e ogni runtime escluso il motivo dell'esclusione. Se il modello non ci sta il contesto si dimezza fino a 2048 prima di scartare il candidato; i candidati remoti (server OpenAI-compatibili, dispositivi accoppiati) contano solo se il profilo lo consente (`allow_remote`) e, per un dispositivo accoppiato, si controlla la memoria che ha dichiarato (se non c'è nessun dato la stima è saltata e la nota lo dice).
- Fallback all'avvio del run, un solo meccanismo con quello di Apple Foundation Models (`FallbackBackend` a catena): se il candidato scelto non parte, non risponde alla salute o fallisce prima del primo evento con un errore di caricamento, si passa al successivo, al massimo 2 volte, mai a metà risposta e mai su un runtime remoto se il profilo non lo consente; con un errore di memoria il candidato dopo parte con un contesto più piccolo. I fallimenti restano in memoria (solo in RAM) per 10 minuti, così il run dopo non riprova subito lo stesso runtime. La scelta e ogni cambio sono nell'evento `aiw.runtime`: in chat compaiono come nota («Ho usato … perché …»); nella vista Sviluppatore anche il dettaglio del percorso.
- API e profili: `GET /api/route?model=…&context=…&remote=…` restituisce la decisione (candidati in ordine con motivo, memoria necessaria, KV stimata, esclusi con motivo). L'editor dei profili ha «Runtime: Automatico» (vista Sviluppatore) con il pannello che mostra la scelta e le alternative; la vista Semplice mostra solo la nota di fallback. `RuntimeInfo.route_priority` nei manifest (24 runtime).
- Limiti del router: `gpu_layers` è riportato ma non applicato (il runtime parte con le sue impostazioni, si applica solo il contesto); la stima della memoria di un server remoto semplice non esiste; mai provato su GPU vere, solo con runtime e dispositivi finti nei test.
- Voce neurale locale (`crates/aiw-engine/src/tts.rs`): le risposte si leggono con **Piper** (eseguibile nel PATH o nella cartella dei runtime di AIW, voce `.onnx` + `.onnx.json`, uscita WAV) o con un **server compatibile OpenAI** (`POST {indirizzo}/v1/audio/speech` con `model`, `input`, `voice`, `response_format: wav`: così si usa Kokoro, vedi README). Impostazione `voice.tts.engine`: `auto` (Piper se c'è l'eseguibile e una voce per la lingua della risposta, poi il server se è indicato, altrimenti le voci del sistema), `system`, `piper`, `openai`. Altre: `voice.tts.voice` (una voce per lingua, di serie la prima), `voice.tts.speed` (0,5–2), `voice.tts.server_url` e `voice.tts.server_model`; l'indirizzo del server è solo a livello di macchina e va validato (http/https).
- Il testo (al massimo 4000 caratteri) viene diviso in frasi, sintetizzato in ordine e riunito in un solo WAV; una sintesi alla volta, annullabile (chiudere la richiesta ferma Piper). Piper parte una volta per frase (non resta caldo). Lingua della risposta: quella indicata, altrimenti una stima dal testo (italiano o inglese), altrimenti `voice.language`.

Nuovo manifest di runtime `piper`.
- Chat e impostazioni: azione «Leggi ad alta voce» su ogni risposta dell'assistente (il pulsante diventa «Ferma la lettura»; Esc ferma); la conversazione a voce usa la voce neurale quando c'è. Lettura frase per frase (la successiva viene richiesta mentre la corrente suona); se il motore fallisce, il resto si legge con la voce del sistema. - Canali («Canali» nell'app, `crates/aiw-engine/src/channels/`): si parla con l'assistente da Telegram, Slack e email. Ogni canale ha `{id, tipo, nome, acceso, assistente, elenco dei mittenti, modalità}` più i segreti; nasce **spento** e non si collega a nulla finché non lo si accende. Chi non è nell'elenco viene scartato e contato («messaggi ignorati da sconosciuti»): non riceve risposta e il testo non arriva mai a un modello. Ogni conversazione esterna diventa una sessione («Telegram · nome», con l'etichetta del canale nell'elenco delle chat); un solo run alla volta per conversazione, con una coda di 5; la risposta finale torna sul canale, spezzata ai limiti della piattaforma e con il Markdown ridotto a testo semplice. Ogni messaggio in entrata e in uscita va nel registro delle attività; al massimo 10 messaggi al minuto per mittente. Gli allegati passano da `attachments.rs`, gli altri si rifiutano con una risposta breve.
- Modalità dei canali: `read_only` (di serie) riusa il percorso di sola lettura dell'assistente proattivo (solo regole di rifiuto, sandbox in sola lettura, conferme negate in automatico); `ask` usa la policy normale e le conferme compaiono nell'app e nel canale (sì/no oppure pulsanti), con scadenza di 10 minuti. La modalità automatica/«yolo» non viene mai rispettata in un canale: diventa `ask` e l'interfaccia lo dice. L'interruttore d'emergenza ferma anche i canali e li spegne, così non si ricollegano al riavvio.
- Telegram: Bot API su HTTPS con long polling, `offset` salvato dopo ogni aggiornamento, allegati con `getFile`, pulsanti in linea per le conferme; abbinamento con `/start <codice>` (codice di 6 cifre, vale 10 minuti, una volta sola, al massimo 5 tentativi). Slack: Socket Mode (`xapp-` → `apps.connections.open` → WebSocket, `xoxb-` per `chat.postMessage`), eventi `message.im` e `app_mention`, ogni busta confermata subito, riconnessione con attesa crescente, pulsanti a blocchi. Email: controllo IMAP, risposta SMTP (587 con STARTTLS, 465 cifrata) nello stesso filo (`In-Reply-To`/`References`) e senza citare l'originale; il mittente deve risultare autenticato (`Authentication-Results` con DKIM o SPF «pass» allineato al dominio del `From`, spegnibile con un avviso); mai risposte a posta `Auto-Submitted`, `Precedence` o `List-Id`; al massimo 10 risposte all'ora per mittente; `\Seen` solo in una cartella dedicata e solo con «segna come letti» acceso, altrimenti gli UID restano nell'archivio.
- Un supervisore avvia e ferma i connettori quando cambiano le impostazioni, con attesa crescente tra i tentativi, e dà a ogni canale uno stato (connesso, errore, spento, non disponibile). I canali si avviano da soli solo nel servizio (`aiw serve`); nell'app desktop li avvia la shell con `Engine::channels_start()`. Sul telefono non lavorano in background.

- OAuth 2.1 per i server HTTP (`POST /api/mcp/servers/{id}/oauth/start`, ritorno su `GET /api/mcp/oauth/callback`, `DELETE /api/mcp/servers/{id}/oauth`): scoperta con `WWW-Authenticate` e metadati della risorsa (RFC 9728) e del server di autorizzazione (RFC 8414), registrazione dinamica (RFC 7591) oppure `oauth_client_id`, codice con PKCE S256, parametro `resource` (RFC 8707), rinnovo con il refresh token. Ogni indirizzo scoperto deve essere https (http solo su questo computer); l'issuer dei metadati e la risorsa devono corrispondere; autorizzazione, token e registrazione devono stare sull'origine dell'issuer; un server che non dichiara S256 è rifiutato. Si aggiunge dall'app (fino a 8 file per volta, 10 MB ciascuno, 25 MB in tutto) o, solo da questo computer, con il percorso di una cartella (fino a 2.000 file da 10 MB, cartelle nascoste e `.gitignore` rispettati); lo stesso contenuto (sha256) non si indicizza due volte e un file cambiato allo stesso percorso sostituisce il vecchio documento. Il lavoro gira in background, con avanzamento e pulsante «Interrompi»; i documenti rimasti «in lavorazione» da un riavvio risultano «non riusciti».

Gli embedding si calcolano in background solo se un runtime di embedding è già in esecuzione (nessun sidecar viene avviato); senza, la ricerca funziona per parole chiave e la pagina lo dice. - Export delle traiettorie: `aiw traces export` e `GET /api/traces/export` scrivono una riga JSON per sessione (messaggi in formato OpenAI, run, decisioni sulle approvazioni), filtrabili per agente, date, stato e numero; i segreti sono mascherati di default e si possono escludere percorsi.

Il messaggio salvato dell'assistente ha ora lo stesso id del messaggio trasmesso in diretta.
- Valutazione degli agenti: nuovo crate `aiw-eval` con suite YAML/JSON (task, file iniziali, grader `file_exists`, `file_contains`, `output_matches`, `json_schema`, `command`, `judge` con un modello come giudice), `aiw eval run <file|id>` con `--repeat`, `--keep` e `--out`, report salvati (`aiw eval list`) e una suite di esempio in `docs/evals/esempio.yaml`. Ogni task gira in una cartella temporanea, senza conferme; le suite si leggono da `~/.aiw/evals`, mai dalla cartella del workspace. `aiw eval compare <A> <B>` confronta due report (differenze per task e totali) e `aiw eval run --profile a --profile b` esegue la suite con più profili e li confronta.

API: `/api/evals`, `/api/evals/{id}/runs`, `/api/eval-runs`, `/api/eval-runs/compare`. L'API non salva suite con grader `command`.

Opzioni modificabili dall'editor visuale. Se scade il limite di un passo `agent`, anche il run dell'agente viene annullato.
- Workflow durevoli: lo stato del run è salvato a ogni passo (tabella `workflow_state`) e all'avvio i run interrotti da un riavvio riprendono dal passo in corso, che ricomincia da capo (almeno una volta); un'approvazione in attesa viene richiesta di nuovo. L'audit registra `decision: "timeout"`. Modificabili dall'editor visuale.

La lezione resta in attesa e viene scritta solo quando l'approvi, anche dopo averla modificata; la cartella del workspace non viene mai toccata. `aiw lessons [list|approve|reject]`, `GET /api/lessons`, `POST /api/lessons/{id}/approve|reject`, `POST /api/sessions/{id}/reflect`; nella UI il pannello «Lezioni da rivedere» della Panoramica, la nota in chat e la voce «Rifletti su questa conversazione». Il prompt dell'agente cambia solo se lo chiedi (`--apply` con conferma, o «Applica all'agente» nella nuova scheda **Ottimizzazioni** della pagina Valutazioni, dopo «Ottimizza il prompt» su una suite). API: `POST /api/evals/{id}/optimize`, `GET /api/prompt-optimizations[/{id}]`, `POST /api/prompt-optimizations/{id}/apply`.

API: `GET /api/trainers`, `GET /api/train/doctor`, `/api/trainers/{id}/install[-plan]`. Il pairing salva classe, memoria e acceleratori del dispositivo accoppiato. Un cambio di adapter riavvia il sidecar.
- Fine-tuning SFT dalle traiettorie: `aiw train sft --base <modello>` crea un dataset dalle sessioni con pollice in su (o riuscite, o dai task superati nei report di valutazione; segreti mascherati, almeno 10 esempi), lancia il trainer (mlx-lm o TRL) in background con log e avanzamento, e registra l'adapter in `~/.aiw/adapters`. Con `--eval <suite> --eval-profile <profilo>` confronta la suite con e senza adapter. `aiw train jobs|logs|cancel|datasets`, `aiw adapters [rm]`. API: `/api/datasets`, `/api/train/jobs`, `/api/adapters`. Pagina **Addestramento** (`#/training`) con dispositivo e trainer, dataset, addestramenti con log e adapter da usare in un profilo.

Solo con TRL o Unsloth (`DPOTrainer` + PEFT). Nella UI il metodo DPO è selezionabile.
- Router a bandit: un agente può elencare `candidate_profiles` e, con l'impostazione `routing.bandit`, ogni run sceglie il profilo con UCB1 (uno mai provato va per primo) usando come reward i pollici su/giù e i task di valutazione superati/falliti. Il profilo scelto compare nello `STATE_SNAPSHOT` e in un evento `aiw.route`. `GET`/`DELETE /api/agents/{id}/routing` per le statistiche e l'azzeramento; nell'editor dell'agente i profili candidati e una tabella con le valutazioni e la reward media.
- RL con reward verificabili: `aiw train grpo --suite <id> --base <modello>` usa i prompt dei task di una suite e come reward la media dei suoi grader che guardano la risposta (`output_matches`, `json_schema`, `judge`; gli altri sono rifiutati). Nuovo `POST /api/evals/{id}/reward {task_id, output}` → `{score, passed, graders}`, protetto come il resto dell'API e documentato in `docs/training.md` per altri framework RL. Metodo `grpo` in `trl_train.py` (`GRPOTrainer`), solo su dispositivi di classe L o superiore.
