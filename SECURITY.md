# Sicurezza

**English summary.** AI Workspace Local (AIW) is a local-first app: it listens on `127.0.0.1` unless you enable LAN access. Report vulnerabilities **privately** through GitHub: *Security* tab → *Report a vulnerability* (Security Advisories) of this repository; please do not open a public issue. Only the latest release receives fixes. The shell sandbox closes the network and hides the app data folder and credential folders on Linux (verified with real bubblewrap) and, with the same rules, on macOS (profile text tested only, never run on a Mac); **on Windows the network cannot be closed and folders cannot be hidden from reads**. MCP stdio servers can be isolated (not on Windows) and need owner approval on first run. **Secrets (provider tokens, MCP headers and variables, OAuth tokens, IMAP passwords, channel and remote-agent credentials, the secret settings) are encrypted at rest** (AES-256-GCM) with a random key that lives in the operating system's keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service), one item; the sealed values stay in the SQLite database and the configuration files. Where there is no keychain (a Linux without a Secret Service or a session, a locked or denied keychain, phones, the Mac App Store build) the secrets stay as they were, nothing fails and the state is declared (`aiw doctor`, Security → Access, the diagnostics). **The encryption does not protect from a program running as your own user** (it can read the keychain item too); it protects from a copy of the disk or of the data folder, a backup, a synchronised folder. The Assistant never sees a secret value (it is typed into a protected field and sent only to a dedicated endpoint that needs full access), and every management action it takes is confirmed by the owner. Known limits are listed below.

## Versioni supportate

AIW è in beta. Le correzioni di sicurezza escono solo per l'**ultima versione rilasciata** (oggi la serie 0.5); le versioni precedenti non ricevono patch.

## Come segnalare una vulnerabilità

Usa la segnalazione privata di GitHub: nel repository apri **Security → Report a vulnerability** (Security Advisories). Così la segnalazione resta riservata finché non c'è una correzione. Non aprire una issue pubblica e non scrivere i dettagli in una discussione o in una pull request.

Indica, se puoi: versione, sistema operativo, passi per riprodurre, cosa ottiene chi attacca. Non esiste un indirizzo email per le segnalazioni: GitHub è l'unico canale.

## Cosa è nell'ambito

- Aggiramento della sandbox della shell, dei limiti dei tool di file o del confine del workspace.
- Aggiramento delle regole di policy, della conferma delle azioni o dell'approvazione dei comandi MCP.
- Lettura o scrittura non autorizzata dell'API locale: token, ambiti (`owner`, `device`, `gateway`, …), pairing, TLS.
- Fuga di segreti (token, chiavi, header) in log, registro delle attività, risposte dell'API o variabili d'ambiente dei processi figli.
- SSRF dai tool `web_fetch` e browser, esecuzione di codice da file, allegati o messaggi dei canali.
- Vulnerabilità nelle dipendenze che AIW rende raggiungibili.

Fuori ambito: attacchi che richiedono già di poter eseguire codice con i tuoi permessi su questo computer; la modalità «Senza freni» con «Nessun contenimento» (fa ciò che puoi fare tu, per scelta); server MCP e provider che hai aggiunto tu e che sono malevoli (si limita il danno con l'isolamento, non lo si elimina); problemi dei runtime di terze parti (llama.cpp, Ollama, …) da segnalare a loro.

## Modello di minaccia (una pagina)

**Local-first.** AIW gira sul tuo computer, con i tuoi dati e i tuoi modelli. Il servizio ascolta su `127.0.0.1`; l'accesso dalla LAN è spento di serie. Non c'è un servizio nostro in mezzo: gli unici invii in uscita sono quelli che configuri (provider di modelli, ricerca web, canali, server MCP).

**Cosa si considera non attendibile.** Il testo prodotto da un modello; il contenuto di pagine web, file, allegati e messaggi dei canali (possono contenere istruzioni ostili, la «prompt injection»); i repository aperti come workspace (la loro configurazione può solo **restringere** le impostazioni di sicurezza, mai allentarle, e non può definire server MCP); gli output dei server MCP e degli agenti remoti; i certificati e i dispositivi mai accoppiati.

**Cosa protegge la sandbox, per sistema.**

| | Linux | macOS | Windows |
|---|---|---|---|
| Scritture fuori dal workspace | negate (bubblewrap) | negate (Seatbelt) | negate (integrità bassa + job object) |
| Rete della shell | **chiusa** di default (`--unshare-net`) | chiusa di default (`(deny network*)`) | **non si può chiudere** |
| Cartella dei dati di AIW e credenziali (`~/.ssh`, `~/.aws`, …) | nascoste | nascoste | **non nascondibili ai comandi** (solo ai tool di file) |
| Variabili d'ambiente segrete | tolte | tolte | tolte |
| Isolamento dei server MCP stdio | sì | sì | **no** |
| Verificato qui | con bubblewrap vero | **solo il testo del profilo** | solo compilazione per `x86_64-pc-windows-gnu` |

Senza sandbox (modalità «Nessun contenimento», Linux senza bubblewrap, Android) i comandi hanno i tuoi privilegi: la barriera è la conferma. Le regole di policy leggono ogni comando di una riga composta, ma non sostituiscono la sandbox. Compromesso noto: con le credenziali nascoste, `git` via SSH non trova la chiave; per consentirlo togli `~/.ssh` da Sicurezza → Sandbox → «Cartelle nascoste» (o usa HTTPS con un token).

**Token e TLS.** L'API usa token con ambiti: `owner` (questo computer), `device` (dispositivi accoppiati), `gateway`, `a2a`, `mcp`. Nel database restano solo gli hash con sale; il token `owner` sta nel file `token` (permessi 0600). Con la LAN accesa conviene `server.tls`: il pairing porta l'impronta SHA-256 del certificato e i client Rust verso un dispositivo accoppiato verificano solo quella. Senza TLS in LAN, codice di pairing e token viaggiano in chiaro.

**Backup e diagnostica.** Un backup di default non contiene chiavi e certificati TLS, token, segreti e credenziali né modelli; con `--include-secrets` i segreti entrano **in chiaro** nell'archivio (aperti con la chiave di questo computer, così si ripristina su qualunque computer), che è marcato `sensitive` ed è sensibile quanto la cartella dei dati di prima: non è cifrato. La copia di sicurezza che il ripristino fa prima di sostituire i dati tiene invece i segreti cifrati con la chiave di questo computer. Creare un backup, ispezionarlo e scaricare la diagnostica richiede il token `owner` (un token `device` riceve 403); il ripristino è solo da CLI con il demone fermo e rifiuta percorsi assoluti, `..`, collegamenti e archivi con schema più nuovo. La diagnostica maschera tutti i segreti e non contiene chat, documenti o posta.

## Segreti, strumenti di gestione dell'Assistente e richieste di segreto

**Dove stanno i segreti: cifrati a riposo, dove c'è un portachiavi (issue #121).** Il valore di un segreto sta nello store, cifrato con una chiave casuale (AES-256-GCM, `ring`); **solo la chiave** sta nel portachiavi del sistema (macOS Keychain, Gestione credenziali di Windows, Secret Service di Linux), in un elemento per cartella dei dati. Un solo punto di innesto (`Store::put_doc/get_doc/list_docs` e `LayeredConfig`) cifra e decifra, e una tabella (`crates/aiw-engine/src/vault/rules.rs`) decide quali documenti sono segreti. Descrizione completa, stati, comandi (`aiw secrets`) e limiti in [docs/segreti.md](docs/segreti.md). Sono cifrati:

- nel database `aiw.db` (SQLite, nella cartella dei dati): i token dei provider di modelli (Hugging Face, ModelScope, …), le variabili d'ambiente e gli header dei server MCP, gli indirizzi con credenziali dentro, i token OAuth dei server MCP, le password IMAP, i token degli agenti remoti, dei canali e dei dispositivi accoppiati, le chiavi API dei motori;
- nei file di configurazione a strati: le impostazioni segrete come `search.brave_api_key`.

Restano **in chiaro** (lavoro separato, #24): il file `token` (permessi 0600) che contiene il token `owner`, le chiavi TLS, gli argomenti (`args`) dei server MCP stdio, e i segreti incollati nella chat. **Dove non c'è un portachiavi** (Linux senza servizio dei segreti o senza sessione grafica, un portachiavi bloccato o negato, iOS e Android, l'app dell'App Store, che con la sandbox non è mai stata provata) i segreti restano in chiaro **e lo stato è dichiarato** (`aiw doctor`, `aiw secrets status`, Sicurezza → Accessi, diagnostica, scheda della richiesta del segreto); non si perde nulla e al primo avvio con un portachiavi si cifrano da soli. Se la chiave sparisce dal portachiavi mentre ci sono valori cifrati, questi non si aprono (stato `key_lost`) ma **non vengono toccati né sostituiti**: si reinseriscono, oppure `aiw secrets forget-unreadable` li toglie (e si rifiuta se il portachiavi è solo irraggiungibile). `security.secrets_at_rest = off` o `aiw secrets decrypt` riportano tutto in chiaro (da fare prima di tornare a una versione precedente).

**La cifratura non protegge da un processo dello stesso utente.** Un programma che gira con i tuoi permessi (per esempio un comando della shell approvato su Windows, dove le cartelle non si possono nascondere in lettura, o un comando non confinato) legge l'elemento nel portachiavi come l'app: macOS chiede il permesso una volta per programma, Windows e quasi tutti i servizi di Linux no. Protegge da una copia del disco o della cartella dei dati, un backup, una cartella sincronizzata, una lettura per errore. Non ripulisce ciò che esisteva prima: i backup fatti prima dell'aggiornamento e le copie di sicurezza in `backups/` hanno i segreti in chiaro, e il filesystem può tenere residui di blocchi riscritti.

Le altre protezioni che esistono sono queste: l'API non restituisce mai i valori (mostra `••••••`), la cartella dei dati è nascosta ai tool di file e, dove la sandbox lo permette, ai comandi della shell (**su Windows i comandi la possono leggere**), il backup di default non contiene i segreti e la diagnostica li maschera.

**Richiesta di un segreto (`aiw_secret_request`).** Il modello non vede mai un valore: indica solo la destinazione (`target`, per esempio `provider_token:hf`), un'etichetta e il motivo. Il motore controlla che la destinazione esista, scrive da sé in parole dove andrà il valore (`destination`, che il modello non può scrivere) ed emette l'evento `aiw.secret_request`, che non ha un campo per il valore. L'utente lo scrive in un campo protetto e il valore viaggia **solo nel corpo di `POST /api/secret-requests/{id}`** (in loopback, o su TLS), poi nella memoria del motore e nella funzione che già scriveva quella destinazione. Non passa da argomenti o risultato dello strumento, eventi, messaggi salvati, riga di audit (`secret.set`, con il solo `target`), richieste di conferma né prompt: un test (`crates/aiw-server/src/tests_harness.rs`) lo cerca nello stream, nel log del run, nei messaggi, nell'audit, nei prompt inviati al modello e nell'elenco dei provider e non lo trova. Prima di scrivere il motore risolve di nuovo la destinazione: se non è più quella mostrata (per esempio il connettore è cambiato) non scrive nulla, chiude la richiesta (409) e il modello non riceve il valore. Un errore della destinazione (un token che il provider rifiuta) è ripulito del valore, la richiesta resta aperta e si può riprovare; un corpo non valido riceve una frase fissa, mai l'eco di ciò che è stato scritto. Un segreto non si chiede con `ask_user` (i campi che lo chiedono sono rifiutati) e `aiw_setting_set` rifiuta le chiavi segrete.

**Ambiti dei token per queste funzioni.** Il valore di un segreto richiede accesso completo (`full`): il computer stesso senza token o il token `owner` su TLS. Un token `device` (un telefono accoppiato) e il token `owner` presentato dalla LAN senza TLS ricevono 403 e la richiesta resta aperta. Un token `device` può invece vedere l'elenco delle richieste (senza valori), rispondere alle domande dell'agente (`/api/questions`) e conferme di strumenti ordinari; un token `gateway` non arriva a nessuna di queste rotte. Su `POST /agui/{agent}` un client dichiara cosa sa mostrare con `forwardedProps.aiw.interactive`, ma la richiesta di segreti si apre solo per un chiamante con accesso completo.

**Le conferme degli strumenti di gestione valgono solo dal proprietario.** Ogni strumento `aiw_*` che modifica qualcosa (14 su 17) ha una regola `ask` incorporata nell'app: chiede conferma in ogni modalità (anche `auto` e `yolo`) e anche dopo «Consenti per la sessione», che per questi strumenti non esiste. La conferma si dà con `POST /api/approvals/{id}`, ma per questi strumenti solo con accesso completo: un token `device` e il token `owner` dalla LAN senza TLS ricevono 403 e la richiesta resta aperta; anche la risposta di un canale (Telegram, Slack, email) è rifiutata, perché i canali rispondono come non proprietari. Gli strumenti funzionano solo in un run di primo livello avviato dal server per una persona: chiamati da un subagente, da un workflow, dal server MCP di AIW (che non li elenca), da un canale, dall'assistente proattivo, da A2A o da `aiw run` sul terminale sono rifiutati senza chiedere conferma. Lo stesso vale per un run avviato da un dispositivo accoppiato (token `device`) che chiama uno strumento che modifica qualcosa: è rifiutato subito, prima che si apra una conferma che nessuno potrebbe dare. L'agente non può cambiare le proprie protezioni: modalità di approvazione, sandbox, rete dei comandi, domini consentiti, tempo di attesa delle conferme, porta, TLS e telemetria sono chiavi che nessuno strumento tocca; non esistono strumenti per regole di policy, hook, token di accesso o pairing; `aiw_agent_save` non crea agenti più liberi (modalità `plan` o `ask`, niente strumenti di gestione né a concessione esplicita).

**Limiti di questa parte (dichiarati):**

- Una regola `allow` scritta dalla persona in Sicurezza per uno strumento di gestione vince sulla regola incorporata: è una sua scelta esplicita, e fa saltare la conferma.
- Un segreto **incollato nella chat** (o scritto in un campo di `render_ui` con `obscured`, che è solo un campo password: il valore viene salvato e inviato al modello) resta nella sessione: messaggi, eventi e prompt delle chiamate successive. L'avviso nel compositore della modalità semplice segnala testo che somiglia a un segreto ma non blocca l'invio. L'export delle tracce nasconde per valore esatto i segreti salvati nell'app e gli schemi noti (`sk-…`, `ghp_…`, `Bearer …`).
- **Checkpoint e rewind non annullano le modifiche di gestione**: coprono solo i file del workspace. Impostazioni, assistenti, connettori, modelli eliminati e segreti si rimettono a mano; gli strumenti riportano il valore precedente dove ha senso e l'audit registra ogni chiamata.
- **Il kill switch** chiude run, conferme, domande e richieste di segreto in attesa, addestramenti, canali, sidecar e browser; **non è verificato** che interrompa download di modelli e installazioni di motori già avviati (non sono run).
- **Iniezione di istruzioni**: testo di pagine, file, posta, risultati di ricerca o risposte di altri agenti può cercare di convincere l'Assistente a un'azione di gestione. Le mitigazioni sono la conferma sempre richiesta e solo dal proprietario (con un avviso nella scheda quando il turno ha letto contenuto esterno), l'assenza di strumenti di lettura di web, file e posta nell'Assistente, la destinazione del segreto calcolata dal motore, le protezioni che l'agente non può cambiare e una regola nel prompt. **Non c'è un blocco automatico** degli strumenti di gestione dopo contenuto non fidato: se chi approva non legge la scheda (per esempio un connettore HTTP di un terzo seguito da una richiesta di token per un suo header) il rischio resta.
- Il giro con un client AG-UI reale non è stato provato, e AG-UI non è qui human-in-the-loop interoperabile (vedi `docs/agui.md`).

## Agenti isolati e credenziali per agente

Dettagli e prove in [docs/agenti-isolati.md](docs/agenti-isolati.md). Un agente può avere una cartella sua (`isolation.dedicated_workspace`) e credenziali sue; di serie nessun agente le ha.

- **Cosa è garantito.** L'agente dedicato lavora in `<dati>/agents/<id>/workspace`, dentro la cartella dei dati che nessun agente vede. Un altro agente non la legge né la scrive (file tool e comandi di shell, anche con `..` e collegamenti simbolici); l'agente dedicato non vede il workspace condiviso, le cartelle consentite dall'utente, l'`AGENTS.md` né le skill del workspace condiviso. Il confine è il run intero: un sotto-agente o un membro di team lavora nella cartella del genitore e con le sue credenziali, e l'handoff da o verso un agente isolato è rifiutato.
- **Cosa non è garantito.** Con la sandbox `off` l'agente legge tutto ciò che legge l'account (per questo un workspace dedicato la vieta). La shell legge il resto del disco come per ogni agente (la sandbox nasconde cartelle precise). **Su Windows, su Linux senza bubblewrap e su Android la shell non può nascondere cartelle**: lì i comandi di un agente possono leggere la cartella di un altro, e a tenerli separati restano i file tool (`aiw agents isolation` lo dice). **Con la rete della shell aperta** i comandi raggiungono l'API locale, che da questo computer senza token vale come accesso completo: nessuna protezione per agente regge (è un limite già noto; `close_shell_network` esiste per questo). I file di una cartella dedicata non sono nel backup. Memorie globali, base di conoscenza, server MCP e connettori sono comuni a tutti gli agenti.
- **Credenziali.** Cifrate dal vault come ogni segreto (con i suoi stessi limiti: non protette da un processo dello stesso utente; in chiaro, con stato dichiarato, dove non c'è un portachiavi). Le imposta solo il proprietario (CLI, `PUT /api/agents/{id}/credentials/{nome}` con ambito `full`): nessuno strumento, impostazione o modello può, e il valore non torna mai da un'API. Le usa il motore, non il modello (`web_fetch_auth`): solo verso gli host indicati, solo in https, ambito ricontrollato a ogni redirect, valore tolto da ciò che il server rimanda (anche se il taglio del testo cade dentro il valore); revoca alla chiamata successiva. Le riceve **solo il run avviato dal proprietario dalla chat** (o da un client AG-UI con accesso completo): non un workflow, `aiw run`, un client A2A o del server MCP, un telefono accoppiato, i run in background e dei canali. Cambiare gli host di una credenziale chiede di rimandare il valore. **Non coprono la shell**: una credenziale nell'ambiente di un comando la vedrebbe il modello con `env`.
- **Un server che rimanda in forma trasformata** il valore (per esempio codificato in base64 o spezzato) non viene ripulito: la ripulitura toglie il valore esatto e la sua codifica percentuale. Dare una credenziale a un host significa fidarsi di che cosa quell'host fa con le richieste.

## Browser controllato: vista live e presa di controllo

Vedi `docs/browser-live.md`. In sintesi:

- **Ambiti.** `/api/browser`, `/api/browser/frame`, `/control`, `/input`, `/dialog` richiedono accesso completo (`full`). **Un token `device` (un telefono accoppiato), `gateway`, A2A o MCP riceve 403: non vede il browser né lo comanda** (la pagina può mostrare una sessione autenticata e l'input remoto equivale ai poteri dell'utente). Decisione esplicita; un ambito dedicato per un telefono non esiste. Un dispositivo accoppiato può invece vedere e chiudere la *domanda* `handover` di un run avviato dal computer (testo di ciò che serve, senza pagina né fotogramma): «Ho finito» da lì restituisce il browser senza che nulla sia stato fatto, e l'agente lo scopre al primo passo.
- **Esclusione reciproca.** L'agente non agisce mentre l'utente è in pausa o guida; l'utente non agisce mentre l'agente ha un'azione in corso. Il kill switch riporta il browser all'agente e chiude la domanda di handover.
- **Credenziali.** Il modello non vede mai password, codici monouso o numeri di carta nei campi riconoscibili: i campi `type=password` e con `autocomplete` `one-time-code`, `current-password`, `new-password`, `cc-*` sono «(nascosto)» negli snapshot e disegnati come pallini negli screenshot. Tasti, testo e fotogrammi dell'utente non sono mai registrati in log, eventi, messaggi, audit né errori (i corpi sono letti con frasi fisse); l'audit ha solo le transizioni e al più il dominio. Dopo la restituzione l'agente vede gli indirizzi senza query né frammento finché non naviga da sé (un login può atterrare su un URL con un codice) e non può agire sui numeri degli elementi di prima. **Eccezioni dichiarate:** `browser_eval` (a concessione esplicita) può leggere qualsiasi cosa la pagina contenga; un campo senza i marcatori sopra (per esempio un PIN in un normale `type=text`) e i campi in un iframe non sono riconosciuti come segreti; il testo scritto nella pagina può comparire nello snapshot dei campi ordinari; con `RUST_LOG` molto verboso altre librerie potrebbero registrare traffico locale, e una direttiva più specifica (`RUST_LOG=tungstenite::protocol=trace`) prevale sul `warn` che teniamo alla libreria WebSocket del browser: non usarla durante un accesso. `GET /api/audit` è leggibile da un dispositivo accoppiato e contiene il dominio delle righe `browser.*`.
- **WebAuthn/passkey** non funzionano con l'input sintetico della vista live: con un browser con finestra, la presa di controllo lo porta in primo piano e si può usare la finestra vera.
- **Chrome già aperto (`browser.attach_url`).** Solo su questo computer (l'indirizzo e la risposta di Chrome devono essere loopback), vietata al workspace e agli strumenti di gestione. L'agente apre schede sue e non vede né intercetta quelle dell'utente, ma **agisce con i cookie di quel profilo**; i download restano a Chrome (non passano dal workspace né dai suoi limiti); alla chiusura non chiude Chrome. Da Chrome 136 la porta di debug è ignorata con il profilo predefinito: serve un profilo dedicato.
- **Download durante la presa di controllo**: non vengono tenuti.

## Limiti noti

Elenco completo e aggiornato in [docs/STATUS.md](docs/STATUS.md) §2.9. In sintesi:

- **Windows**: rete dei comandi non chiudibile, cartelle non nascondibili in lettura, server MCP non isolabili (servirebbe un AppContainer o regole del firewall).
- **macOS**: il profilo Seatbelt non è mai stato eseguito su un Mac.
- **Mac App Store (App Sandbox)**: gli agenti vedono solo la cartella dell'app più le cartelle che l'utente consente col pannello di macOS (Impostazioni → Cartelle consentite). Solo l'utente le aggiunge: nessuna rotta dell'API, impostazione, strumento o modello lo fa. Lì i tool di file leggono e scrivono ma non eliminano; la cartella dei dati e i luoghi di `sandbox.deny_read` (anche alla vera cartella personale) restano nascosti. Il pannello vero e una build firmata con i certificati dello store non sono stati provati; `shell` e MCP non ricevono quelle cartelle. Vedi `docs/store/README.md`.
- Non coperti dalla sandbox: socket dell'agente SSH e `/run/user`, hook, valutatori degli eval, browser controllato. Server MCP «non isolati» (quelli già presenti prima di questa versione) girano con l'ambiente e i permessi dell'app finché non premi «Isola».
- Wrapper che nascondono il comando vero (`ssh host «…»`, `docker run …`, interpreti con script propri) non vengono aperti dall'analisi delle regole di policy.
- Token e TLS: il token `owner` è in chiaro nel file `token`; un browser su un altro dispositivo mostra un avviso finché non installa l'autorità locale; niente fissaggio dell'impronta per server MCP e agenti A2A inseriti a mano.
- **Segreti cifrati a riposo solo dove c'è un portachiavi** (macOS, Windows, Linux con Secret Service; altrove restano in chiaro e lo stato è dichiarato), e comunque non protetti da un processo dello stesso utente; il file `token` e le chiavi TLS restano in chiaro (#24); segreti incollati nella chat o in un campo `obscured` di `render_ui` restano nella sessione; checkpoint e rewind non annullano le modifiche di gestione dell'Assistente; il kill switch non è verificato su download e installazioni già avviati (dettagli nella sezione precedente).
- Agenti isolati: nessun confine con la sandbox `off`; su Windows la shell non separa gli agenti; nessuna interfaccia grafica per l'isolamento e le credenziali; contenitori Docker/Podman solo valutati (`docs/agenti-isolati.md`).
- Protezione SSRF dietro un proxy: non implementata.
- Dipendenze: dopo l'aggiornamento di `rusqlite` e `async-executor`, `cargo audit` non segnala vulnerabilità. Restano avvisi di crate non più mantenuti (`proc-macro-error`, `smartstring`, `ttf-parser`, `unsafe-libyaml`, `zbus_names`, `zvariant`, `zvariant_derive`) e `glib` 0.18.5 (RUSTSEC-2024-0429, serve un aggiornamento di Tauri/GTK), tutti senza correzione compatibile. Non sono ignorati. Un workflow (`.github/workflows/audit.yml`) li ricontrolla a ogni modifica dei lockfile e ogni settimana.
